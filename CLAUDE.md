## Architecture

- **Access token lives only in memory** — `lib/token-store.ts` is a module-level singleton (not React state) holding the current token plus a registered refresh-handler callback, so the low-level `lib/api-client.ts` (plain `fetch` wrapper) can attach `Authorization` headers and trigger a refresh-and-retry-once on a 401 without importing React/context.
- **`lib/auth-context.tsx`** (`AuthProvider`) owns the actual React state (`user`, `accessToken`, `isLoading`) and is the only thing that calls `login`/`register`/`logout`/`refresh`. On mount it silently calls `/auth/refresh` (cookie-based) to restore a session; the in-flight refresh promise is de-duped (`refreshInFlight` ref) so a page-load refresh and an API-triggered refresh-on-401 don't race.
- **`components/orders-panel.tsx` follows the same reusable-`api`-prop pattern as `customer-streams-panel.tsx`** — `OrdersPanelApi` (`listOrders`/`createOrder`/`cancelOrder`/`listPlans`/`searchStreams`) defaults to the admin routes (`lib/orders-api.ts`, `lib/plans-api.ts`); `app/reseller/dashboard/page.tsx` passes a module-level `ORDERS_API` built from `lib/reseller-orders-api.ts`/`lib/reseller-plans-api.ts` instead, plus a `priceField` prop (`'customer_price'` for admin, `'reseller_price'` for resellers) so the same component shows the right price without knowing which portal it's in. Same stable-reference requirement as `STREAMS_API` — don't inline the object.
- **`/reseller/*` is a third, fully parallel auth stack** (`reseller-token-store.ts`/`reseller-api-client.ts`/`reseller-auth-context.tsx`, scoped to `app/reseller/layout.tsx`) — same shape as the customer one below, for resellers who manage their own subset of customers. `components/customer-streams-panel.tsx` (the stream-assignment picker) takes an optional `api` prop (`CustomerStreamsPanelApi`: `listCustomerStreams`/`assignCustomerStreams`/`searchAvailableStreams`) defaulting to the admin-scoped functions in `lib/customer-streams-api.ts` — `app/reseller/dashboard/page.tsx` passes a **module-level** `STREAMS_API` constant built from `lib/reseller-customer-streams-api.ts` instead. That object must stay a stable reference (not an inline literal), since it's a dependency of the panel's data-loading `useCallback`/`useEffect`s — an inline object would change identity every render and refetch in a loop.
- **`/customer/*` is a second, fully parallel auth stack for the customer portal** — `lib/customer-token-store.ts`, `lib/customer-api-client.ts`, `lib/customer-auth-context.tsx` (`CustomerAuthProvider`/`useCustomerAuth`) mirror the admin/user `token-store.ts`/`api-client.ts`/`auth-context.tsx` file-for-file but are entirely separate module instances — a customer session and an admin session never share an in-memory token or a refresh handler, matching the backend's separate `customer-auth` cookie/token namespace. `CustomerAuthProvider` is scoped to `app/customer/layout.tsx` (not the root layout), so its silent-refresh-on-mount only fires for `/customer/*` pages, not every admin page. `components/customer-protected-route.tsx` + `components/customer-shell.tsx` mirror `protected-route.tsx`/`dashboard-shell.tsx` for the same reason.
- **`components/protected-route.tsx`** is a client-side gate (redirects to `/login` once `isLoading` is false and there's no user) — there's deliberately no Next.js `proxy.ts`/middleware gate, since the refresh cookie is httpOnly and unreadable by the client, and verifying it requires the backend anyway. **`/customer/login`, `/reseller/login`, and the bare `/customer`/`/reseller` index pages run the inverse check**: once `isLoading` is false, an already-authenticated visitor is redirected straight to that portal's `/dashboard` instead of seeing the login form again (the bare index pages exist solely to do this redirect — `/customer`/`/reseller` render nothing themselves). The admin `/login` deliberately does **not** have this — only the two token-restoring portals do.
- **Field-level form errors**: the backend returns `message: string[]` for validation failures; `lib/form-errors.ts#groupFieldErrors` buckets those strings by field name via substring match so the register form can show errors under the right input without the backend needing a structured per-field error shape.
- **Tab titles are set client-side, not via Next's Metadata API**: every page is a Client Component (`'use client'`), and `metadata` exports only work in Server Components, so `lib/use-page-title.ts#usePageTitle('Page Name')` sets `document.title = "{APP_NAME} | {Page Name}"` directly. **Non-obvious gotcha it works around**: Next's root-layout `<title>` is a real React-reconciled element, not static HTML — any re-render of an ancestor (e.g. `AuthProvider`'s initial-mount `isLoading: true → false` flip after the silent `/auth/refresh` settles) resets it back to the layout's static `metadata.title`. Pages behind `ProtectedRoute` are shielded from this by accident (their content doesn't mount until after that flip), but unprotected pages (`/login`, `/register`) mount immediately and lose a plain `document.title = ...` within milliseconds. `usePageTitle` works around it with a `MutationObserver` on the `<title>` element that re-applies the desired text if anything else changes it — don't simplify this back to a bare assignment without re-testing `/login`/`/register` specifically.

## UI theme

The UI follows a "Flussonic-inspired" visual language: dark navy navbar, blue→violet gradient hero with a dot-grid pattern, pink/magenta pill CTAs. Tokens are CSS custom properties in `src/app/globals.css` (`--flu-navy`, `--flu-blue`, `--flu-violet`, `--flu-pink*`), exposed as Tailwind v4 theme colors (`bg-flu-navy`, `text-flu-pink`, `shadow-flu-pink/30`, etc.) plus a `.flu-hero-gradient` utility class for the gradient + dot pattern. `components/auth-shell.tsx` (login/register wrapper) and `components/dashboard-shell.tsx` (sidebar + topbar) are where this is applied — reuse these tokens/components rather than introducing new one-off colors when adding pages.
