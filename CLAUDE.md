# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run start:dev` — dev server with watch, on `PORT` (default 3001), routes under `/api/v1`
- `npm run build` / `npm run start:prod` — production build + run
- `npm run lint` — eslint --fix
- `npm run test` — jest unit tests; `npx jest path/to/file.spec.ts` for a single file
- `npm run test:e2e` / `npm run test:cov` — e2e / coverage
- `npm run migration:run` / `npm run migration:revert` — apply/undo TypeORM migrations against `DB_*` env vars
- `npm run migration:generate -- src/database/migrations/Name` — diff entities vs DB schema
- `npm run seed` — seeds `admin@example.com` / `user@example.com` (password `ChangeMe123!`), skips users that already exist

Requires MySQL 8.0.13+ (the `users` migration's `id` column uses an `UUID()` expression default, which needs that version) and a `.env` copied from `.env.example`.

## Architecture

Everything auth-related lives under `src/auth/` plus `src/users/`.

- **Two Passport strategies, two guards**: `jwt-access` (`strategies/jwt-access.strategy.ts`) reads `Authorization: Bearer`; `jwt-refresh` (`strategies/jwt-refresh.strategy.ts`) reads the token from the `refresh_token` **cookie**, not a header, via a custom extractor. `JwtAccessGuard` / `JwtRefreshGuard` (`guards/`) wrap them for `@UseGuards`.
- **Refresh tokens are httpOnly cookies, never JSON**. `auth/utils/cookie.util.ts` sets/clears them, scoped to `path: /api/v1/auth` so the cookie isn't sent on unrelated routes. `POST /auth/refresh` rotates both the access token and the refresh cookie on every call (sliding session — there's no refresh-token blacklist or DB-backed revocation).
- **RBAC is decorator-driven and forward-compatible**: `UserRole` enum (`users/enums/user-role.enum.ts`, currently `admin`/`user`) + `@Roles(...)` decorator + `RolesGuard` (`auth/decorators/roles.decorator.ts`, `auth/guards/roles.guard.ts`) read `request.user.role`, populated by whichever JWT guard ran first. Adding a role is just adding an enum value — no guard changes needed.
- **Password hash never leaves the service layer**: `User.password_hash` (`users/entities/user.entity.ts`) has `select: false` (TypeORM excludes it from default queries) *and* `@Exclude()` (class-transformer strips it if it's ever loaded), enforced globally via `ClassSerializerInterceptor` in `main.ts`. `UsersService.findByEmailWithPassword()` is the one place that explicitly `.addSelect()`s it, used only for login.
- **Errors** all funnel through `common/filters/http-exception.filter.ts` into `{ statusCode, message, error, path, timestamp }`. `message` is a string array for validation errors, from the global `ValidationPipe` (`whitelist: true, forbidNonWhitelisted: true` — unknown body fields are rejected, not silently dropped).
- **Config** is centralized in `config/configuration.ts` (nested object) with `config/env.validation.ts` (class-validator) enforced via `ConfigModule.forRoot({ validate })` in `app.module.ts` — the app won't boot on missing/invalid env vars.
- **`APP_ENV`, not `NODE_ENV`**: the app-level environment flag (`development`/`production`/`test`, drives TypeORM query logging + the refresh cookie's `secure` flag) is deliberately its own var (`configService.get('appEnv')`), kept separate from the Node-ecosystem-standard `NODE_ENV` that other tooling may read. `database/data-source.ts` (the TypeORM CLI's standalone datasource) reads `process.env.APP_ENV` directly since it runs outside Nest's DI. `APP_NAME` is a separate product-name var used in the Swagger doc title (`main.ts`) — matches the frontend's `NEXT_PUBLIC_APP_NAME`.
- **Two separate DB connections by design**: `database/data-source.ts` is the `DataSource` used by the TypeORM CLI (migrations/seed scripts run outside Nest's DI container). `app.module.ts`'s `TypeOrmModule.forRootAsync` is the runtime connection used by the app itself. Both list entities manually — keep them in sync if the entity list changes.
- Login/register are throttled per-IP (`@Throttle` in `auth.controller.ts`) on top of the global `ThrottlerModule` default, via `@nestjs/throttler`.
- **`created_at`/`updated_at` are UTC unix seconds, not MySQL DATETIME/TIMESTAMP**, across every table (`users`, `customers`, `flussonic_servers`, `flussonic_server_stats`). Columns are `BIGINT UNSIGNED` with `unixTimestampTransformer` (`common/utils/unix-timestamp.util.ts`) converting MySQL's string bigint to a plain JS `number`. Since MySQL can't auto-populate a plain bigint the way it does `DEFAULT CURRENT_TIMESTAMP`, every entity sets these itself via `@BeforeInsert`/`@BeforeUpdate` hooks — a new entity needs the same two hooks (copy the pattern from `users/entities/user.entity.ts`), not `@CreateDateColumn`/`@UpdateDateColumn`. `users`/`customers` were retroactively converted from DATETIME via `ConvertUsersTimestampsToUnix*`/`ConvertCustomersTimestampsToUnix*` migrations (add→`UNIX_TIMESTAMP()`-populate→drop-and-rename).
- **`flussonic_servers` CRUD is admin-only** (`src/flussonic-servers/`): `@UseGuards(JwtAccessGuard, RolesGuard)` + `@Roles(UserRole.ADMIN)` on the whole controller — unlike `customers`, which any authenticated user can manage.
- **`flussonic_server_stats` is a nested resource**: `FlussonicServerStatsController` is `@Controller('flussonic-servers/:serverId/stats')` (same module, same admin-only guards). `findAllForServer`/`create`/`sync` all call `FlussonicServersService.findOne(serverId)` first so an unknown or soft-deleted server 404s before touching the stats table. Decimal columns (`cpu_usage`, `memory_usage_percent`, `network_in/out_mbps`) come back from MySQL as strings (TypeORM avoids float precision loss on `DECIMAL`), so the service converts numbers to strings on the way in; the frontend strips trailing zeros for display (`formatDecimal` in the stats page).
- **`flussonic_servers.last_total_clients`/`last_uptime_seconds`** are a denormalized cache of the most recent successful sync's `total_clients`/`uptime`, written by `markSynced()` alongside `flussonic_version`/`status` — so the servers **list** endpoint/page can show current-ish clients/uptime without joining or querying `flussonic_server_stats` per row. They're stale between syncs and untouched by `markUnreachable()` (last-known values are kept visible even while a server is unreachable, rather than being cleared).
- **`POST .../stats/sync` is the real Flussonic integration** (`FlussonicServerStatsService.sync`): builds the target URL as `https://{domain}:443/{api_base_path}/{api_version_tag}/config/stats` if `use_ssl`, else `http://{hostname}:{port}/...`; always authenticates with `Authorization: Bearer <api_access_token>` (see `api_access_token` below — never HTTP Basic). The full JSON response is mapped onto typed columns (see `mapResponseToStat` — `online_streams`→`active_streams`, `input_kbit`/`output_kbit`÷1000→Mbps, disk usage computed from the `root` entry in `partitions`, etc.) **and** stored verbatim in `raw_response` (a JSON column) specifically so future features can read fields we haven't added dedicated columns for yet without another migration. On success, the parent server's `flussonic_version` and `status` (→ `ACTIVE`) are updated; on any fetch/parse failure, `status` → `UNREACHABLE` and a 502 is thrown — in both cases `status` is left alone if it's currently `MAINTENANCE` or `DELETED` (an automated sync shouldn't override an intentional manual state). `FlussonicServerStatsService.syncAll` (its own stats-only bulk sync, still callable directly) syncs every non-deleted server sequentially, catching per-server failures so one bad server doesn't abort the batch. The old manual `POST .../stats` (no `/sync`) still exists and still works, but the UI only exposes "Sync"/"Sync all" now. Uses the global `fetch`/`AbortController` (Node's built-in undici, no HTTP client dependency added), with an 8s timeout per server. Known gap: no self-signed-cert bypass, so an `https` server with an untrusted cert will show as unreachable.
- **`POST /flussonic-servers/sync-all` runs stats + streams + sessions, not just stats**: `FlussonicServersController.syncAll` delegates to `FlussonicSyncAllService` (new, lives in this module to avoid circular DI — it depends on `FlussonicServersService`/`FlussonicServerStatsService`/`FlussonicStreamsService`/`FlussonicStreamSessionsService`, none of which depend back on it). For each active server it calls the three per-server sync primitives (`statsService.sync`, `streamsService.syncFromFlussonic`, `sessionsService.syncFromFlussonic`) independently via a shared `tryRun` wrapper — one sync type failing for one server never blocks the other two sync types for that server, or any sync type for other servers. Response is `{ total, results: [{ serverId, name, stats, streams, sessions }] }` (each an `{ ok, error?, created?, updated? }`), a breaking shape change from the old stats-only `{ total, succeeded, failed, results }` — there's a single frontend consumer so no back-compat was kept.
- **`api_access_token` is derived, not client-supplied**: `computeFlussonicAccessToken` (`flussonic-servers/utils/access-token.util.ts`) is `base64("<api_username>:<api_password>")` — Flussonic's own scheme, identical encoding to HTTP Basic auth, just sent as `Bearer`. `FlussonicServersService.create`/`update` compute and store it (encrypted) automatically whenever username or password changes; neither DTO accepts `api_access_token` directly. `ensureAccessToken(server)` self-heals rows that predate this field (computes + persists on first use) — relevant for any server created before this convention existed. **Do not reintroduce a manually-editable access-token field** — if the format ever needs to change again, add a new data migration (see `FixFlussonicAccessTokenSeparator*`) rather than relying on self-heal alone, since self-heal only fires when the column is `NULL`.
- **`api_password_enc`/`api_access_token` are reversibly encrypted, not hashed**: unlike `User.password_hash` (bcrypt, one-way), the app needs the plaintext back to authenticate against the real Flussonic API (see `sync` above), so they're AES-256-GCM encrypted via `common/utils/encryption.util.ts` (`encryptSecret`/`decryptSecret`) using `CREDENTIALS_ENCRYPTION_KEY` (64-char hex, `openssl rand -hex 32`) — a required env var, validated in `env.validation.ts`. Still `@Exclude()`d from every API response like the password hash.
- **`customers.username`/`customers.password_hash`**: bcrypt-hashed like `User.password_hash` (`select: false` + `@Exclude()`), not AES-encrypted like the Flussonic credentials — the app never needs the plaintext back. `username` is required on create and unique (nullable at the DB level only because pre-existing rows predate the column — see `AddUsernamePasswordToCustomers*`); `CreateCustomerDto` requires both, `UpdateCustomerDto` (via `PartialType`) makes both optional so an edit can omit `password` to leave it unchanged. `CustomersService.create`/`update` strip `password` out of the DTO before `Object.assign`/`repository.create` (the entity has no `password` field, only `password_hash`) and hash it via the same `bcryptSaltRounds` config as `AuthService`.
- **`flussonic_streams` name uniqueness is checked in two places, not just the DB**: `FlussonicStreamsService.create` always rejects a name that already exists in the local `flussonic_streams` cache (409, no override — two local rows can't reference the same upstream stream). It *also* calls `nameExistsOnFlussonic` (a live `GET streams/urlencode(name)` against the real server) to catch a stream that exists upstream but isn't in our cache (created outside this app, or the cache drifted) — that case 409s too, unless the request sets `confirmOverwrite: true` on `CreateFlussonicStreamDto`, since Flussonic's `PUT` is a blind upsert that would otherwise silently replace someone else's stream config. `GET .../streams/check-name?name=...` exposes both checks read-only (`{ existsInDb, existsOnServer }`) so the frontend can warn *before* the user submits, instead of just reacting to a 409. This route is registered before `:id` in the controller — Nest/Express match routes in declaration order, so a literal path segment must come before a dynamic one with the same HTTP verb or it'll never be reached.
- **`flussonic_streams.live_stats_json` is populated by a separate sync path, never by create/update**: `POST .../streams/sync` (`FlussonicStreamsService.syncFromFlussonic`) calls the real Flussonic `GET streams` endpoint, which is cursor-paginated (`next`/`prev`, opaque tokens) rather than page/limit — `fetchAllLiveStreams` follows `next` until it's absent or `MAX_SYNC_PAGES` (100) is hit. Each returned stream's raw object (live `stats`, per-input stats, `media_info` track lists, `config_on_disk`, etc.) is stored verbatim in `live_stats_json` for a matching local row (matched by name, same as `assertNameAvailable`); a stream that exists upstream but has no *active* local row (soft-deleted counts as "no row" — see `nameExistsInDb`/`findByNameInDb`, both filter `status != deleted`) gets a new row created from its `config_on_disk`. This means a stream can reappear as a fresh row if its local copy was soft-deleted but it's still live upstream — that's intentional, not a bug, since it surfaces real drift between our records and Flussonic. `config_json` on already-known rows is never touched by sync, only by create/update, so it stays "what we'll `PUT` back on the next edit" — a separate concern from "what's actually running right now".
- **Renaming a stream is delete-old + create-new, not a real rename**: `UpdateFlussonicStreamDto` accepts `name` again (`PartialType(CreateFlussonicStreamDto)`, not `OmitType`). `FlussonicStreamsService.update` treats a `name` that differs from the stored `config_json.name` as a rename: it runs the same DB/live-server uniqueness check as `create` (409 unless `confirmOverwrite: true`), `PUT`s the merged config under the *new* name first, and only `DELETE`s the *old* name from Flussonic if that succeeds — so a failed create leaves the old stream intact rather than losing it. The local row's `id` doesn't change, only `config_json.name`.
- **`flussonic_stream_sessions` is an upserted log, not a create/edit resource**: `FlussonicStreamSessionsService.syncFromFlussonic` calls the real Flussonic `GET sessions` — a single flat, cursor-paginated list covering *every* stream on the server at once (not nested per-stream), unlike `GET streams`. Each entry is upserted by its Flussonic session id (`session_uuid`, unique-indexed) so an ongoing session gets refreshed in place across syncs rather than duplicated; `flussonic_stream_id` is resolved via `FlussonicStreamsService.findByNameInDb` (made public for this) and left `null` if no local stream matches. Timestamps (`started_at`/`updated_at`) arrive from Flussonic in **milliseconds** — converted to unix seconds (`toUnixSeconds`) to match this app's convention, unlike every other field which is stored verbatim. Sessions have no `flussonic_server_id` column of their own (not in the original spec), so `findAllForServer` attributes them to a server by inner-joining through the matched stream — a session whose stream was never locally synced (`flussonic_stream_id IS NULL`) simply won't appear in any server's list, even though the row still exists in the table.
- **New sessions get IP geolocation via `IPWHOIS_API_URL`** (`common/utils/ipwhois.util.ts#fetchIpWhoIs`, defaults to `https://ipwho.is`, optional env var): only called once, when a session is first inserted (not on every sync refresh, since the IP for a given session doesn't change) — the full response is stored verbatim in `ipwhois_json`. Always best-effort: any failure (timeout, non-2xx, network error) resolves to `null` rather than throwing, so a flaky/rate-limited lookup never fails the whole sync. With dozens of new sessions on a first sync, expect this to take a while (sequential lookups, ~5s timeout each) — the sync endpoint has no artificial time budget of its own, so a slow client-side timeout can look like a failure even though the sync completes successfully server-side.
- **`flussonic_stream_sessions.synced_at` identifies "still live" without a separate sync-run table**: `syncFromFlussonic` captures one `nowUnixSeconds()` value at the start of the call and stamps it on every row it creates *or* updates that pass — not `Date.now()` per row, since rows touched in the same run must compare equal. `findAllForServer`'s `?latestOnly=true` filters to `session.synced_at = MAX(synced_at)` (scoped to the server via the same stream join used elsewhere), so a row left over from an earlier sync — the session ended and Flussonic stopped reporting it — silently drops out of the "current" view without ever being deleted. Don't confuse this with `updated_at`, which is Flussonic's *own* session-progress timestamp, not ours.
- **`customers` and `flussonic_servers` never hard-delete** — `remove()` in both services sets `status = *Status.DELETED` and saves instead of calling `repository.remove()`. `findAll`/`findOne` in both services always exclude `status = DELETED` (via a `where`/`Not()` clause), so soft-deleted rows disappear from every normal read path but the row physically remains. `create`/`update` reject `status: 'deleted'` in the request body with a 400 (`assertSettableStatus`) — deletion must go through the `DELETE` endpoint, not a status edit. Note: unique constraints (`customers.phone`, `flussonic_servers.(hostname, port)`) aren't relaxed for soft-deleted rows, so a deleted customer's phone number (or a deleted server's hostname:port) stays reserved and can't be reused by a new row. `users` has no delete endpoint at all, so it wasn't touched.
