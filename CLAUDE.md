# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — dev server on `http://localhost:3000`
- `npm run build` / `npm run start` — production build + serve
- `npm run lint` — eslint
- No test runner is configured in this app

Requires `.env.local` copied from `.env.example` (`NEXT_PUBLIC_API_URL` pointing at the backend's `/api/v1`, `NEXT_PUBLIC_APP_NAME` for the product name shown in tab titles).

## Architecture

- **Access token lives only in memory** — `lib/token-store.ts` is a module-level singleton (not React state) holding the current token plus a registered refresh-handler callback, so the low-level `lib/api-client.ts` (plain `fetch` wrapper) can attach `Authorization` headers and trigger a refresh-and-retry-once on a 401 without importing React/context.
- **`lib/auth-context.tsx`** (`AuthProvider`) owns the actual React state (`user`, `accessToken`, `isLoading`) and is the only thing that calls `login`/`register`/`logout`/`refresh`. On mount it silently calls `/auth/refresh` (cookie-based) to restore a session; the in-flight refresh promise is de-duped (`refreshInFlight` ref) so a page-load refresh and an API-triggered refresh-on-401 don't race.
- **`components/orders-panel.tsx` follows the same reusable-`api`-prop pattern as `customer-streams-panel.tsx`** — `OrdersPanelApi` (`listOrders`/`createOrder`/`cancelOrder`/`listPlans`/`listAssignedStreams`) defaults to the admin routes (`lib/orders-api.ts`, `lib/plans-api.ts`, `lib/customer-streams-api.ts#listCustomerStreams`); `app/reseller/dashboard/page.tsx` passes a module-level `ORDERS_API` built from `lib/reseller-orders-api.ts`/`lib/reseller-plans-api.ts`/`lib/reseller-customer-streams-api.ts#listMyCustomerStreams` instead, plus a `priceField` prop (`'customer_price'` for admin, `'reseller_price'` for resellers) so the same component shows the right price without knowing which portal it's in. Same stable-reference requirement as `STREAMS_API` — don't inline the object. **`listAssignedStreams` returns only streams already assigned to the customer** (not a cross-server "available" search) — an order provisions a plan onto a stream the customer already holds, so the stream `<select>` shows nothing until one's been assigned via the streams picker first. **`paymentMethods` prop** (defaults to every method) restricts the payment-method `<select>` — the reseller dashboard passes `['wallet']` only, which the panel renders as read-only text instead of a single-option dropdown; the backend independently rejects any reseller order whose `payment_method` isn't `'wallet'`, so this is UX, not the real enforcement. **Duration is no longer entered here** — it comes from the selected plan's `duration_days` (shown next to the price preview), since `Plan` now carries its own duration (`plan-form-panel.tsx` has a required "Duration (days)" field). **`OrdersPanelApi.getWalletBalance`** (optional, omitted for admin) is fetched alongside orders/plans/streams in the same `load()` call and shown as "Current balance: X" under the payment-method field when set — only the reseller dashboard provides it (`getMyWalletBalance` from `lib/reseller-wallet-api.ts`), since only reseller orders are wallet-billed; the backend's insufficient-balance error message already states the shortfall (`current balance is X, this requires Y`), so this display is a heads-up, not duplicate math.
- **`Order` carries a full invoicing snapshot now (customer/plan/stream), so `OrderInvoiceDialog`'s callers must never override `stream_name`/`stream_title`/`stream_ingest_domain` with a live lookup** — `orders-panel.tsx` and `app/customer/dashboard/page.tsx` both only enrich the optional `server_name` field (not part of the snapshot, since a stream's hosting server doesn't affect billing terms) from their locally-loaded streams list; overriding the snapshot fields would silently show a renamed stream's *current* name on a historical invoice, defeating the point of freezing it at purchase time.
- **`components/order-invoice-dialog.tsx` reads straight off `Order`'s invoicing-snapshot fields, no extra fetch** — `customer_name`/`customer_email`/`customer_phone`/`customer_company_name`/`customer_address`/`customer_city`/`customer_state`/`customer_pincode`/`plan_name`/`plan_description` are already on every order returned by the backend (frozen at purchase time), so the dialog just formats what it's handed. Wired up on `app/dashboard/reports/page.tsx` — clicking an order number opens it; there's no reseller/customer-portal equivalent yet, only the admin reports page.
- **`/reseller/*` is a third, fully parallel auth stack** (`reseller-token-store.ts`/`reseller-api-client.ts`/`reseller-auth-context.tsx`, scoped to `app/reseller/layout.tsx`) — same shape as the customer one below, for resellers who manage their own subset of customers. `components/customer-streams-panel.tsx` (the stream-assignment picker) takes an optional `api` prop (`CustomerStreamsPanelApi`: `listCustomerStreams`/`assignCustomerStreams`/`searchAvailableStreams`) defaulting to the admin-scoped functions in `lib/customer-streams-api.ts` — `app/reseller/dashboard/page.tsx` passes a **module-level** `STREAMS_API` constant built from `lib/reseller-customer-streams-api.ts` instead. That object must stay a stable reference (not an inline literal), since it's a dependency of the panel's data-loading `useCallback`/`useEffect`s — an inline object would change identity every render and refetch in a loop.
- **`/customer/*` is a second, fully parallel auth stack for the customer portal** — `lib/customer-token-store.ts`, `lib/customer-api-client.ts`, `lib/customer-auth-context.tsx` (`CustomerAuthProvider`/`useCustomerAuth`) mirror the admin/user `token-store.ts`/`api-client.ts`/`auth-context.tsx` file-for-file but are entirely separate module instances — a customer session and an admin session never share an in-memory token or a refresh handler, matching the backend's separate `customer-auth` cookie/token namespace. `CustomerAuthProvider` is scoped to `app/customer/layout.tsx` (not the root layout), so its silent-refresh-on-mount only fires for `/customer/*` pages, not every admin page. `components/customer-protected-route.tsx` + `components/customer-shell.tsx` mirror `protected-route.tsx`/`dashboard-shell.tsx` for the same reason.
- **`components/protected-route.tsx`** is a client-side gate (redirects to `/login` once `isLoading` is false and there's no user) — there's deliberately no Next.js `proxy.ts`/middleware gate, since the refresh cookie is httpOnly and unreadable by the client, and verifying it requires the backend anyway. **`/customer/login`, `/reseller/login`, and the bare `/customer`/`/reseller` index pages run the inverse check**: once `isLoading` is false, an already-authenticated visitor is redirected straight to that portal's `/dashboard` instead of seeing the login form again (the bare index pages exist solely to do this redirect — `/customer`/`/reseller` render nothing themselves). The admin `/login` deliberately does **not** have this — only the two token-restoring portals do.
- **Field-level form errors**: the backend returns `message: string[]` for validation failures; `lib/form-errors.ts#groupFieldErrors` buckets those strings by field name via substring match so the register form can show errors under the right input without the backend needing a structured per-field error shape.
- **Tab titles are set client-side, not via Next's Metadata API**: every page is a Client Component (`'use client'`), and `metadata` exports only work in Server Components, so `lib/use-page-title.ts#usePageTitle('Page Name')` sets `document.title = "{APP_NAME} | {Page Name}"` directly. **Non-obvious gotcha it works around**: Next's root-layout `<title>` is a real React-reconciled element, not static HTML — any re-render of an ancestor (e.g. `AuthProvider`'s initial-mount `isLoading: true → false` flip after the silent `/auth/refresh` settles) resets it back to the layout's static `metadata.title`. Pages behind `ProtectedRoute` are shielded from this by accident (their content doesn't mount until after that flip), but unprotected pages (`/login`, `/register`) mount immediately and lose a plain `document.title = ...` within milliseconds. `usePageTitle` works around it with a `MutationObserver` on the `<title>` element that re-applies the desired text if anything else changes it — don't simplify this back to a bare assignment without re-testing `/login`/`/register` specifically.
- **`components/wallet-topup-dialog.tsx` and `components/wallet-transactions-panel.tsx` are shared between the reseller and customer wallets, not duplicated** — `WalletTopupDialog` takes a generic `entityName` prop (not `resellerName`) since it's just display text; `WalletTransactionsPanel` is generic over `T extends WalletTransactionLike` (id/amount/balance_after/remark/created_at) so it accepts either `WalletTransaction` (reseller, `types/wallet.ts`) or `CustomerWalletTransaction` (customer) without caring which. Four API modules feed them: `lib/wallet-api.ts` + `lib/reseller-wallet-api.ts` (admin-scoped and reseller-portal-scoped reseller wallet) and `lib/customer-wallet-api.ts` + `lib/customer-wallet-portal-api.ts` (same split for customers) — same admin-vs-portal pairing used everywhere else (orders, streams, plans). `app/dashboard/resellers/page.tsx` and `app/dashboard/customers/page.tsx` both wire up a topup dialog + history panel this way; `components/reseller-shell.tsx` and `components/customer-shell.tsx` both show a balance pill in the header that opens the same history panel, and `app/reseller/dashboard/page.tsx`/`app/customer/dashboard/page.tsx` both repeat it as a summary card on the page itself.
- **IP geolocation for sessions is looked up client-side, never through our backend** — `lib/client-ipwhois.ts#lookupIp` calls `https://ipwho.is/<ip>` directly from the browser (in-memory cache keyed by IP, so a page of sessions with repeat IPs only looks each one up once) instead of the backend doing it during sync, since a server hammering a rate-limited free API from one IP exhausts it fast while many browsers sharing the load rarely does. `components/stream-sessions-panel.tsx` (customer/reseller) and `app/dashboard/servers/[id]/sessions/page.tsx` (admin) both run the same "collect unique IPs on the current page → `Promise.all` lookups → merge into a `Record<ip, IpWhoIsInfo|null>` state" effect. The backend's `ip_lookup_url` field (see backend `CLAUDE.md`) is rendered as a manual "Look up IP" link/cell alongside this. **No map** — an OpenStreetMap/React-Leaflet pin view was tried and explicitly removed; don't re-add `leaflet`/`react-leaflet` without being asked. `components/stream-sessions-panel.tsx` also hardcodes `latestOnly: true` with no visible toggle (unlike the admin sessions page, which keeps its toggle) — the customer/reseller portals only ever show currently-live sessions. It also auto-refreshes every 30s (`AUTO_REFRESH_INTERVAL_MS`) and on manual refresh-button click via a *silent* reload (separate `isRefreshing` state) that keeps the current list on screen instead of blanking it behind the full `isLoading` spinner, which is reserved for the initial load/page-change fetch. The header shows a live `{total} total` count from the paginated response.
- **`components/stream-details-panel.tsx`'s "Raw sync data" `<details>` block is admin-only** — a `showRawData` prop (default `true`) gates it; `components/customer-assigned-streams-panel.tsx` forwards its own `showRawData` prop (default `true`) through to the panel, and both `app/reseller/dashboard/page.tsx` (via that prop) and `app/customer/dashboard/page.tsx` (direct `StreamDetailsPanel` usage) pass `false` — the raw JSON dump is internal debugging info, not something to show a reseller/customer. The customer/reseller portals reach `StreamDetailsPanel` via a new `getStreamDetails` field on `CustomerAssignedStreamsPanelApi` (`lib/customer-portal-api.ts#getMyStreamDetails`, `lib/reseller-customer-streams-api.ts#getMyStreamDetails`) hitting new ownership-checked backend routes (`GET customer-auth/streams/:streamId`, `GET reseller-auth/streams/:streamId`) — the "view details" eye-icon button in both `CustomerAssignedStreamsPanel` and the customer dashboard's own inline stream list only renders when `getStreamDetails` is provided, replacing the old boolean `showViewDetails` prop.
- **`components/stream-player.tsx` embeds a Clappr player (`@clappr/core` + `@clappr/hlsjs-playback`, pinned to the exact `hls.js` version the plugin's peer dep demands) for live preview** — `StreamDetailsPanel` renders it in a "Preview" section (top of the panel, above Protocols) whenever `stream.ingest_domain` is set *and* `config_json.protocols.hls` is enabled, reusing the exact same `https://{domain}/{name}/index.m3u8` formula as `buildOutputUrls`'s HLS entry. Clappr touches `window`/the DOM at import time, so both packages are dynamically `import()`ed inside a `useEffect` (destroyed/recreated on `src` change) rather than at module scope — this sidesteps SSR entirely without needing `next/dynamic`'s `ssr: false`, since nothing runs until after mount. Neither package ships accurate types (`@clappr/core`'s bundled `.d.ts` is auto-generated from JSDoc and omits real options like `plugins` or percentage-string `width`/`height`; `@clappr/hlsjs-playback` has no types at all — see `src/types/clappr-hlsjs-playback.d.ts`), so the constructor options are built as a plain `Record<string, unknown>` and cast once at the `new Player(...)` call rather than fighting the incomplete declared type field-by-field.
- **`OrdersPanelApi.getWalletBalance` is keyed by `customerId` now, not zero-arg** — admin passes `getCustomerWalletBalance` (from `lib/customer-wallet-api.ts`, uses the arg) as its default; the reseller portal still passes `getMyWalletBalance` (from `lib/reseller-wallet-api.ts`, ignores the arg — a reseller's orders are always billed to their *own* wallet, never the customer's) — TypeScript allows this since a function with fewer declared params is assignable to a type expecting more. The "Current balance" line under the payment-method field now shows whenever the *currently selected* `paymentMethod === 'wallet'`, not just when `paymentMethods.length === 1` — admin's dropdown has 5 options and the balance line needs to react to which one is picked, not just render once for reseller's fixed single option.

## UI theme

The UI follows a "Flussonic-inspired" visual language: dark navy navbar, blue→violet gradient hero with a dot-grid pattern, pink/magenta pill CTAs. Tokens are CSS custom properties in `src/app/globals.css` (`--flu-navy`, `--flu-blue`, `--flu-violet`, `--flu-pink*`), exposed as Tailwind v4 theme colors (`bg-flu-navy`, `text-flu-pink`, `shadow-flu-pink/30`, etc.) plus a `.flu-hero-gradient` utility class for the gradient + dot pattern. `components/auth-shell.tsx` (login/register wrapper) and `components/dashboard-shell.tsx` (sidebar + topbar) are where this is applied — reuse these tokens/components rather than introducing new one-off colors when adding pages.
