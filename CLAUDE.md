# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run start:dev` — dev server with watch, on `PORT` (default 3001), routes under `/api/v1`
- `npm run build` / `npm run start:prod` — production build + run
- `npm run lint` — eslint --fix
- `npm run test` — jest unit tests; `npx jest path/to/file.spec.ts` for a single file
- `npm run test:e2e` / `npm run test:cov` — e2e / coverage
- `npm run migration:run` / `npm run migration:revert` — apply/undo TypeORM migrations against `DB_*` env vars
- `npm run migration:generate -- src/database/migrations/Name` — diff entities vs DB schema
- `npm run seed` — seeds `admin@example.com` / `user@example.com` (password `ChangeMe123!`), skips users that already exist

Requires MySQL 8.0.13+ (the `users` migration's `id` column uses an `UUID()` expression default, which needs that version) and a `.env` copied from `.env.example`.

## Architecture

Everything auth-related lives under `src/auth/` plus `src/users/`.

- **Two Passport strategies, two guards**: `jwt-access` (`strategies/jwt-access.strategy.ts`) reads `Authorization: Bearer`; `jwt-refresh` (`strategies/jwt-refresh.strategy.ts`) reads the token from the `refresh_token` **cookie**, not a header, via a custom extractor. `JwtAccessGuard` / `JwtRefreshGuard` (`guards/`) wrap them for `@UseGuards`.
- **Refresh tokens are httpOnly cookies, never JSON**. `auth/utils/cookie.util.ts` sets/clears them, scoped to `path: /api/v1/auth` so the cookie isn't sent on unrelated routes. `POST /auth/refresh` rotates both the access token and the refresh cookie on every call (sliding session — there's no refresh-token blacklist or DB-backed revocation).
- **RBAC is decorator-driven and forward-compatible**: `UserRole` enum (`users/enums/user-role.enum.ts`, currently `admin`/`user`) + `@Roles(...)` decorator + `RolesGuard` (`auth/decorators/roles.decorator.ts`, `auth/guards/roles.guard.ts`) read `request.user.role`, populated by whichever JWT guard ran first. Adding a role is just adding an enum value — no guard changes needed.
- **Password hash never leaves the service layer**: `User.password_hash` (`users/entities/user.entity.ts`) has `select: false` (TypeORM excludes it from default queries) *and* `@Exclude()` (class-transformer strips it if it's ever loaded), enforced globally via `ClassSerializerInterceptor` in `main.ts`. `UsersService.findByEmailWithPassword()` is the one place that explicitly `.addSelect()`s it, used only for login.
- **Errors** all funnel through `common/filters/http-exception.filter.ts` into `{ statusCode, message, error, path, timestamp }`. `message` is a string array for validation errors, from the global `ValidationPipe` (`whitelist: true, forbidNonWhitelisted: true` — unknown body fields are rejected, not silently dropped).
- **Config** is centralized in `config/configuration.ts` (nested object) with `config/env.validation.ts` (class-validator) enforced via `ConfigModule.forRoot({ validate })` in `app.module.ts` — the app won't boot on missing/invalid env vars.
- **`APP_ENV`, not `NODE_ENV`**: the app-level environment flag (`development`/`production`/`test`, drives TypeORM query logging + the refresh cookie's `secure` flag) is deliberately its own var (`configService.get('appEnv')`), kept separate from the Node-ecosystem-standard `NODE_ENV` that other tooling may read. `database/data-source.ts` (the TypeORM CLI's standalone datasource) reads `process.env.APP_ENV` directly since it runs outside Nest's DI. `APP_NAME` is a separate product-name var used in the Swagger doc title (`main.ts`) — matches the frontend's `NEXT_PUBLIC_APP_NAME`.
- **Two separate DB connections by design**: `database/data-source.ts` is the `DataSource` used by the TypeORM CLI (migrations/seed scripts run outside Nest's DI container). `app.module.ts`'s `TypeOrmModule.forRootAsync` is the runtime connection used by the app itself. Both list entities manually — keep them in sync if the entity list changes.
- Login/register are throttled per-IP (`@Throttle` in `auth.controller.ts`) on top of the global `ThrottlerModule` default, via `@nestjs/throttler`.
- **`created_at`/`updated_at` are UTC unix seconds, not MySQL DATETIME/TIMESTAMP**, across every table (`users`, `customers`, `flussonic_servers`, `flussonic_server_stats`). Columns are `BIGINT UNSIGNED` with `unixTimestampTransformer` (`common/utils/unix-timestamp.util.ts`) converting MySQL's string bigint to a plain JS `number`. Since MySQL can't auto-populate a plain bigint the way it does `DEFAULT CURRENT_TIMESTAMP`, every entity sets these itself via `@BeforeInsert`/`@BeforeUpdate` hooks — a new entity needs the same two hooks (copy the pattern from `users/entities/user.entity.ts`), not `@CreateDateColumn`/`@UpdateDateColumn`. `users`/`customers` were retroactively converted from DATETIME via `ConvertUsersTimestampsToUnix*`/`ConvertCustomersTimestampsToUnix*` migrations (add→`UNIX_TIMESTAMP()`-populate→drop-and-rename).
- **`flussonic_servers` CRUD is admin-only** (`src/flussonic-servers/`): `@UseGuards(JwtAccessGuard, RolesGuard)` + `@Roles(UserRole.ADMIN)` on the whole controller — unlike `customers`, which any authenticated user can manage.
- **`flussonic_server_stats` is a nested resource**: `FlussonicServerStatsController` is `@Controller('flussonic-servers/:serverId/stats')` (same module, same admin-only guards). `findAllForServer`/`create`/`sync` all call `FlussonicServersService.findOne(serverId)` first so an unknown or soft-deleted server 404s before touching the stats table. Decimal columns (`cpu_usage`, `memory_usage_percent`, `network_in/out_mbps`) come back from MySQL as strings (TypeORM avoids float precision loss on `DECIMAL`), so the service converts numbers to strings on the way in; the frontend strips trailing zeros for display (`formatDecimal` in the stats page).
- **`flussonic_servers.last_total_clients`/`last_uptime_seconds`** are a denormalized cache of the most recent successful sync's `total_clients`/`uptime`, written by `markSynced()` alongside `flussonic_version`/`status` — so the servers **list** endpoint/page can show current-ish clients/uptime without joining or querying `flussonic_server_stats` per row. They're stale between syncs and untouched by `markUnreachable()` (last-known values are kept visible even while a server is unreachable, rather than being cleared).
- **`POST .../stats/sync` is the real Flussonic integration** (`FlussonicServerStatsService.sync`): builds the target URL as `https://{domain}:443/{api_base_path}/{api_version_tag}/config/stats` if `use_ssl`, else `http://{hostname}:{port}/...`; always authenticates with `Authorization: Bearer <api_access_token>` (see `api_access_token` below — never HTTP Basic). The full JSON response is mapped onto typed columns (see `mapResponseToStat` — `online_streams`→`active_streams`, `input_kbit`/`output_kbit`÷1000→Mbps, disk usage computed from the `root` entry in `partitions`, etc.) **and** stored verbatim in `raw_response` (a JSON column) specifically so future features can read fields we haven't added dedicated columns for yet without another migration. On success, the parent server's `flussonic_version` and `status` (→ `ACTIVE`) are updated; on any fetch/parse failure, `status` → `UNREACHABLE` and a 502 is thrown — in both cases `status` is left alone if it's currently `MAINTENANCE` or `DELETED` (an automated sync shouldn't override an intentional manual state). `FlussonicServerStatsService.syncAll` (its own stats-only bulk sync, still callable directly) syncs every non-deleted server sequentially, catching per-server failures so one bad server doesn't abort the batch. The old manual `POST .../stats` (no `/sync`) still exists and still works, but the UI only exposes "Sync"/"Sync all" now. Uses the global `fetch`/`AbortController` (Node's built-in undici, no HTTP client dependency added), with an 8s timeout per server. Known gap: no self-signed-cert bypass, so an `https` server with an untrusted cert will show as unreachable.
- **`POST /flussonic-servers/sync-all` runs stats + streams + sessions, not just stats**: `FlussonicServersController.syncAll` delegates to `FlussonicSyncAllService` (new, lives in this module to avoid circular DI — it depends on `FlussonicServersService`/`FlussonicServerStatsService`/`FlussonicStreamsService`/`FlussonicStreamSessionsService`, none of which depend back on it). For each active server it calls the three per-server sync primitives (`statsService.sync`, `streamsService.syncFromFlussonic`, `sessionsService.syncFromFlussonic`) independently via a shared `tryRun` wrapper — one sync type failing for one server never blocks the other two sync types for that server, or any sync type for other servers. Response is `{ total, results: [{ serverId, name, stats, streams, sessions }] }` (each an `{ ok, error?, created?, updated? }`), a breaking shape change from the old stats-only `{ total, succeeded, failed, results }` — there's a single frontend consumer so no back-compat was kept.
- **`src/settings/` — one admin-configurable cron schedule per sync type, not per server**: `sync_schedules` has exactly 3 rows (`server_stats`/`streams`/`sessions`, seeded by migration, `sync_type` unique-indexed), each firing across *every* non-deleted server, not a specific one. `SyncScheduleService` (implements `OnModuleInit`) is both the CRUD layer and the scheduler: on boot it loads all 3 rows and calls `applySchedule` for each; `update()` persists the change first, then calls `applySchedule` again so the running job reflects it immediately (no restart needed). `applySchedule` always deletes the existing `SchedulerRegistry` job for that type first (`doesExist('cron', name)` / `deleteCronJob`), then re-adds a fresh `CronJob` only if `enabled` — this is the only way to change a `CronJob`'s schedule, since the `cron` package's jobs aren't mutable in place. A `cron_expression` is validated by just constructing a throwaway `CronJob` with it inside a try/catch (`new CronJob(expr, () => {})` — a no-op callback that's never started) before saving; a malformed expression 400s instead of corrupting the schedule or crashing later inside the actual cron tick. `runJob` dispatches to whichever of `statsService.syncAll()` / `streamsService.syncAllServers()` / `sessionsService.syncAllServers()` matches the type, then re-fetches and saves the row with `last_run_at`/`last_run_summary` — errors thrown by the sync call are caught and stored as `{ error }` in `last_run_summary` rather than crashing the cron tick (an uncaught exception inside a `CronJob`'s callback would otherwise kill that job silently). `FlussonicStreamsService.syncAllServers()`/`FlussonicStreamSessionsService.syncAllServers()` exist *only* for this — the "Sync all" button's `FlussonicSyncAllService` still does its own per-server interleaved loop and doesn't call these, so don't be surprised the "loop every active server for one sync type" logic exists in two places for two different composition needs (per-server-multi-type vs. per-type-multi-server).
- **`sync_schedule_runs` is an append-only log; `sync_schedules.last_run_at`/`last_run_summary` is just the latest snapshot**: every `runJob` firing now also inserts a `SyncScheduleRun` row (`sync_type`, `ran_at`, `success`, `summary`) *before* updating the `SyncSchedule` row — `success` is tracked directly from the try/catch (not inferred from the summary's shape), so a sync call that resolves but reports internal per-server failures (`summary.failed > 0`) still counts as `success: true` at the run-log level; only a thrown exception from the sync call itself is `success: false`. Rows are never pruned or deleted, so `GET /settings/sync-schedules/:type/runs` (paginated, newest-first via `SyncScheduleService.findRuns`) is the only way to see anything before the most recent firing.
- **`sync_schedules.manual_sync_enabled` gates the frontend's manual "Sync"/"Sync all" buttons, independently of `enabled` (which only gates the cron)**: enforced by `SyncScheduleGateService` (`src/flussonic-servers/sync-schedule-gate.service.ts`), which reads `sync_schedules` via its **own** `TypeOrmModule.forFeature([SyncSchedule])` registration in `FlussonicServersModule` — not by importing `SettingsModule`'s `SyncScheduleService`, since `SettingsModule` already depends on `FlussonicServersModule` for the sync services and importing back would be a circular module dependency. This is the one place in `flussonic-servers` allowed to touch a "foreign" entity directly, specifically to break that cycle. The check is called from `FlussonicServerStatsController.sync`/`FlussonicStreamsController.sync`/`FlussonicStreamSessionsController.sync` (`assertManualSyncEnabled`, throws 403) and from `FlussonicSyncAllService.syncAll` (`isManualSyncEnabled`, checked once per type up front and skipped gracefully per-server rather than thrown, consistent with `syncAll`'s existing "one failure never blocks the rest" behavior). **Critically, this check must never be added inside the shared per-server `sync()`/`syncFromFlussonic()` methods themselves** — the cron scheduler's `runJob` calls `statsService.syncAll()`/`streamsService.syncAllServers()`/`sessionsService.syncAllServers()`, which loop and call those exact same per-server methods internally; putting the gate there would make disabling the manual button also silently break the independent cron schedule.
- **`api_access_token` is derived, not client-supplied**: `computeFlussonicAccessToken` (`flussonic-servers/utils/access-token.util.ts`) is `base64("<api_username>:<api_password>")` — Flussonic's own scheme, identical encoding to HTTP Basic auth, just sent as `Bearer`. `FlussonicServersService.create`/`update` compute and store it (encrypted) automatically whenever username or password changes; neither DTO accepts `api_access_token` directly. `ensureAccessToken(server)` self-heals rows that predate this field (computes + persists on first use) — relevant for any server created before this convention existed. **Do not reintroduce a manually-editable access-token field** — if the format ever needs to change again, add a new data migration (see `FixFlussonicAccessTokenSeparator*`) rather than relying on self-heal alone, since self-heal only fires when the column is `NULL`.
- **`api_password_enc`/`api_access_token` are reversibly encrypted, not hashed**: unlike `User.password_hash` (bcrypt, one-way), the app needs the plaintext back to authenticate against the real Flussonic API (see `sync` above), so they're AES-256-GCM encrypted via `common/utils/encryption.util.ts` (`encryptSecret`/`decryptSecret`) using `CREDENTIALS_ENCRYPTION_KEY` (64-char hex, `openssl rand -hex 32`) — a required env var, validated in `env.validation.ts`. Still `@Exclude()`d from every API response like the password hash.
- **`customers.username`/`customers.password_hash`**: bcrypt-hashed like `User.password_hash` (`select: false` + `@Exclude()`), not AES-encrypted like the Flussonic credentials — the app never needs the plaintext back. `username` is required on create and unique (nullable at the DB level only because pre-existing rows predate the column — see `AddUsernamePasswordToCustomers*`); `CreateCustomerDto` requires both, `UpdateCustomerDto` (via `PartialType`) makes both optional so an edit can omit `password` to leave it unchanged. `CustomersService.create`/`update` strip `password` out of the DTO before `Object.assign`/`repository.create` (the entity has no `password` field, only `password_hash`) and hash it via the same `bcryptSaltRounds` config as `AuthService`.
- **`flussonic_streams` name uniqueness is checked in two places, not just the DB**: `FlussonicStreamsService.create` always rejects a name that already exists in the local `flussonic_streams` cache (409, no override — two local rows can't reference the same upstream stream). It *also* calls `nameExistsOnFlussonic` (a live `GET streams/urlencode(name)` against the real server) to catch a stream that exists upstream but isn't in our cache (created outside this app, or the cache drifted) — that case 409s too, unless the request sets `confirmOverwrite: true` on `CreateFlussonicStreamDto`, since Flussonic's `PUT` is a blind upsert that would otherwise silently replace someone else's stream config. `GET .../streams/check-name?name=...` exposes both checks read-only (`{ existsInDb, existsOnServer }`) so the frontend can warn *before* the user submits, instead of just reacting to a 409. This route is registered before `:id` in the controller — Nest/Express match routes in declaration order, so a literal path segment must come before a dynamic one with the same HTTP verb or it'll never be reached.
- **`flussonic_streams.live_stats_json` is populated by a separate sync path, never by create/update**: `POST .../streams/sync` (`FlussonicStreamsService.syncFromFlussonic`) calls the real Flussonic `GET streams` endpoint, which is cursor-paginated (`next`/`prev`, opaque tokens) rather than page/limit — `fetchAllLiveStreams` follows `next` until it's absent or `MAX_SYNC_PAGES` (100) is hit. Each returned stream's raw object (live `stats`, per-input stats, `media_info` track lists, `config_on_disk`, etc.) is stored verbatim in `live_stats_json` for a matching local row (matched by name, same as `assertNameAvailable`); a stream that exists upstream but has no *active* local row (soft-deleted counts as "no row" — see `nameExistsInDb`/`findByNameInDb`, both filter `status != deleted`) gets a new row created from its `config_on_disk`. This means a stream can reappear as a fresh row if its local copy was soft-deleted but it's still live upstream — that's intentional, not a bug, since it surfaces real drift between our records and Flussonic. `config_json` on already-known rows is never touched by sync, only by create/update, so it stays "what we'll `PUT` back on the next edit" — a separate concern from "what's actually running right now".
- **Renaming a stream is delete-old + create-new, not a real rename**: `UpdateFlussonicStreamDto` accepts `name` again (`PartialType(CreateFlussonicStreamDto)`, not `OmitType`). `FlussonicStreamsService.update` treats a `name` that differs from the stored `config_json.name` as a rename: it runs the same DB/live-server uniqueness check as `create` (409 unless `confirmOverwrite: true`), `PUT`s the merged config under the *new* name first, and only `DELETE`s the *old* name from Flussonic if that succeeds — so a failed create leaves the old stream intact rather than losing it. The local row's `id` doesn't change, only `config_json.name`.
- **`flussonic_stream_sessions` is an upserted log, not a create/edit resource**: `FlussonicStreamSessionsService.syncFromFlussonic` calls the real Flussonic `GET sessions` — a single flat, cursor-paginated list covering *every* stream on the server at once (not nested per-stream), unlike `GET streams`. Each entry is upserted by its Flussonic session id (`session_uuid`, unique-indexed) so an ongoing session gets refreshed in place across syncs rather than duplicated; `flussonic_stream_id` is resolved via `FlussonicStreamsService.findByNameInDb` (made public for this) and left `null` if no local stream matches. Timestamps (`started_at`/`updated_at`) arrive from Flussonic in **milliseconds** — converted to unix seconds (`toUnixSeconds`) to match this app's convention, unlike every other field which is stored verbatim. Sessions have no `flussonic_server_id` column of their own (not in the original spec), so `findAllForServer` attributes them to a server by inner-joining through the matched stream — a session whose stream was never locally synced (`flussonic_stream_id IS NULL`) simply won't appear in any server's list, even though the row still exists in the table.
- **New sessions get IP geolocation via `IPWHOIS_API_URL`** (`common/utils/ipwhois.util.ts#fetchIpWhoIs`, defaults to `https://ipwho.is`, optional env var): only called once, when a session is first inserted (not on every sync refresh, since the IP for a given session doesn't change) — the full response is stored verbatim in `ipwhois_json`. Always best-effort: any failure (timeout, non-2xx, network error) resolves to `null` rather than throwing, so a flaky/rate-limited lookup never fails the whole sync. With dozens of new sessions on a first sync, expect this to take a while (sequential lookups, ~5s timeout each) — the sync endpoint has no artificial time budget of its own, so a slow client-side timeout can look like a failure even though the sync completes successfully server-side.
- **`flussonic_stream_sessions.synced_at` identifies "still live" without a separate sync-run table**: `syncFromFlussonic` captures one `nowUnixSeconds()` value at the start of the call and stamps it on every row it creates *or* updates that pass — not `Date.now()` per row, since rows touched in the same run must compare equal. `findAllForServer`'s `?latestOnly=true` filters to `session.synced_at = MAX(synced_at)` (scoped to the server via the same stream join used elsewhere), so a row left over from an earlier sync — the session ended and Flussonic stopped reporting it — silently drops out of the "current" view without ever being deleted. Don't confuse this with `updated_at`, which is Flussonic's *own* session-progress timestamp, not ours.
- **`src/plans/` + `src/orders/` add a subscription/billing layer shared by customers and resellers**: `plans` is a single catalog (`show_customer`/`show_reseller` booleans gate visibility per audience) with two price columns — `customer_price` (direct sale) and `reseller_price` (always server-computed as `mrp * (1 - reseller_percentage/100)` in `PlansService.computeResellerPrice`, never accepted directly from the client; recomputed on every `create`/`update` where `mrp` or `reseller_percentage` changes). `orders` maps one `(plan_id, stream_id, customer_id)` to a purchase: `OrdersService.create` **snapshots** the plan's `price`/`duration_days`/`max_streams`/`max_connections`/`playback_protocols` onto the order row at purchase time (deliberately duplicated, not live-joined) — a later edit to a plan's price/limits must never alter an order that was already sold. `reseller_id` on the order is likewise a point-in-time snapshot of the customer's reseller at purchase, independent from the live `customers.reseller_id` (which can change later). The one caller-supplied difference between the admin and reseller creation paths is `priceField` (`'customer_price'` vs `'reseller_price'`) passed into the shared `OrdersService.create()` — everything else (conflict checking, snapshotting, stream assignment) is identical code.
- **An order creation call assigns the stream; cancelling it unassigns**: `OrdersService.create` calls `FlussonicStreamsService.assignSingleStreamToCustomer` (new — unlike `assignToCustomer` used by the manual streams picker, this adds one stream without touching the customer's other assignments, and still 409s if the stream already belongs to a different customer) *before* the order row is even created — if that assignment fails, no order or payment record exists for a stream the customer didn't actually get. `updateStatus`/`updateStatusForCustomer` transitioning `status` to `cancelled` calls `unassignSingleStreamFromCustomer`, which is a no-op (not an error) if the stream was already reassigned elsewhere since — cancelling an old order should never steal a stream back from whoever has it now. **Known gap**: the older manual "assign streams" picker (`customers/:id/streams`, full-replace semantics) and the order-driven single-stream assignment are two independent code paths against the same `flussonic_streams.customer_id` column — manually unassigning a stream via the picker does *not* cancel or flag any order still referencing it, so an admin using both features on the same customer can create an inconsistency between "what the picker shows" and "what an active order thinks it granted." No reconciliation exists yet.
- **A stream can only be under one active order's date window at a time — `OrdersService.resolveEffectiveFrom` auto-queues overlapping renewals instead of allowing duplicates**: before computing `effective_to`, `create()` looks up the existing `status = 'active'` order for the same `stream_id` with the furthest-out `effective_to` (there can be more than one historically, hence `ORDER BY effective_to DESC LIMIT 1` rather than assuming uniqueness) — if one exists and its window extends past the requested `effective_from`, the new order's `effective_from` is silently pushed to start exactly when that one ends, chaining correctly across repeated renewals (the 3rd order chains off the 2nd's end, not the 1st's). This only ever fires for the *same* customer renewing/extending — a different customer requesting an actively-held stream still hits the pre-existing `assignSingleStreamToCustomer` 409 conflict (checked after this date resolution, since date math never needs to know who currently holds the stream). No new `OrderStatus` was added for "scheduled/future" orders — a queued renewal is still `status: 'active'` immediately; only `effective_from`/`effective_to` communicate that it hasn't started yet, so any UI showing "current" orders must compare against those timestamps, not just filter by `status`.
- **`GET /orders/reports` is a read-only enrichment layer over `findAll`, not a separate data model**: `OrdersController.findAllWithDetails` (must stay declared before the `:id` route) calls `OrdersService.findAllWithDetails` (paginated, same `QueryOrderDto` filters as `findAll`) and `getSummary` (aggregate `COUNT`/`SUM` over every matching row, ignoring pagination) in parallel, merging them into one response. Enrichment (`OrdersService.toReportEntries`) batch-fetches `customer_name`/`plan_name`/`stream_name`+`server_name`/`reseller_name` via new `findByIds` methods on `CustomersService`/`PlansService`/`ResellersService` and `FlussonicStreamsService.findByIdsAsDirectoryEntries` — deliberately **including soft-deleted/inactive rows** (unlike every other read path in this app), so a historical order's labels still resolve to something readable ("Unknown customer" as the only fallback) even after the customer/plan/stream/reseller it referenced was later deleted. `getSummary`'s `paidRevenue` filters to `payment_status = 'paid'` while `totalValue` sums every matching order regardless of payment state — don't conflate the two when adding new summary figures.
- **`customer_action_settings` gates *who* can edit/delete/assign-streams on a customer — one row per `(actor_type, action)` pair (admin/reseller × edit/delete/assign, 6 rows total, all default-enabled)**: same shape and reasoning as `order_cancel_settings` below, just two dimensions instead of one. `CustomerActionSettingsService.assertActionEnabled(actorType, action)` is called at the top of the relevant controller method — `CustomersController.update`/`.remove` and `CustomerStreamsController.assign` for `ADMIN`, `ResellerCustomersController.update`/`.remove` and `ResellerCustomerStreamsController.assignCustomerStreams` for `RESELLER` — never inside `CustomersService`, since the service's methods are shared by both actor types and by the reseller's own `createForReseller`/`findAllForReseller` (which aren't gated at all — only edit/delete/assign are covered, not create/list). `CustomersModule` now imports `SettingsModule` for this (safe: `SettingsModule` has no dependency back on `CustomersModule`). No customer-facing equivalent exists — customers never edit/delete/assign-streams on *other* customers, so there's no `CUSTOMER` value in `CustomerActionActor`. The reseller portal's read-only mirror lives on the same `ResellerSettingsController` as the order-cancel one (`GET reseller-auth/settings/customer-actions`, returns all three flags in one call rather than three separate ones).
- **`order_cancel_settings` gates *who* can cancel an order — one row per actor type (admin/reseller/customer), all default-enabled**: `OrderCancelSettingsService.assertCancelEnabled(actorType)` (in `SettingsModule`, exported for other modules) is called from `OrdersService.applyStatusUpdate` **only** when a status update is actually transitioning to `cancelled` — every other field (payment_status, remark, or a no-op re-cancel) is unaffected, so disabling a role's cancel button never blocks their other order edits. `OrdersService.updateStatus`/`updateStatusForCustomer`/`cancelForCustomer` each thread through a fixed `OrderCancelActor` matching their own route (`ADMIN`/`RESELLER`/`CUSTOMER` respectively) — the actor type is never client-supplied. `OrdersModule` importing `SettingsModule` (for this one service) is safe: `SettingsModule` has no dependency back on `OrdersModule`/`CustomerAuthModule`/`ResellerAuthModule`, only on `FlussonicServersModule`. The reseller/customer portals can't call the admin-only `GET /settings/order-cancel` (wrong JWT strategy entirely), so each portal gets its own tiny read-only mirror instead: `GET reseller-auth/settings/order-cancel-enabled` / `GET customer-auth/settings/order-cancel-enabled`, both just wrapping `isCancelEnabled` for that one actor type — no write path, only admin can flip the switch.
- **`customer-auth/orders/:id/cancel` is the customer portal's only order-mutating endpoint** — customers can list (`GET`) and cancel their own orders, nothing else; there's no general `PATCH` for them the way admin/reseller have, since a customer should never be able to touch `payment_status`/`remark`/etc.
- **`orders.payment_status` is separate from `orders.status`** — deliberately two state machines: `status` (active/expired/cancelled/suspended) is the subscription/grant lifecycle; `payment_status` (pending/paid/failed/refunded/cancelled) is the money side, ready for a payment gateway (`gateway_transaction_id`/`gateway_response_json` columns exist but are unused until one is wired up — new orders default to `payment_status: 'paid'` since there's currently no async gateway step, only manual payment recording). `order_number` (e.g. `ORD-2026-000001`) is generated in a second `save()` call after insert, once the auto-increment `id` is known — it can't be computed before the row exists.
- **`src/resellers/` + `src/reseller-auth/` add a third principal type sitting between admin and `Customer`**: `resellers` is structurally identical to `customers` (phone/username/password_hash, soft-delete via `status`), and `reseller-auth` is a third parallel auth stack mirroring `customer-auth` (own strategies `reseller-jwt-access`/`reseller-jwt-refresh`, own cookie `reseller_refresh_token` at `/api/v1/reseller-auth`, own `type: 'reseller'` payload marker). `customers.reseller_id` (nullable FK, app-enforced like `flussonic_streams.customer_id`) is the actual relationship: **a reseller has many customers, a customer at most one reseller**. `CustomersService` gained reseller-scoped twins of every CRUD method (`findAllForReseller`/`findOneForReseller`/`createForReseller`/`updateForReseller`/`removeForReseller`) rather than threading an optional `resellerId` through the existing admin methods — keeps the "is this scoped or not" question resolvable by which method you called, not by an easy-to-forget parameter. `createForReseller`/`updateForReseller` always destructure `reseller_id` out of the incoming DTO and discard it (`void reseller_id`) — a reseller's own `reseller_id` is only ever set by the controller from `@CurrentReseller()`, never from the request body, even though `CreateCustomerDto`/`UpdateCustomerDto` do accept an admin-settable `reseller_id` field for the plain `/customers` admin routes. `ResellerCustomerStreamsController` (`reseller-auth/customers/:customerId/streams`, `reseller-auth/streams`) reuses `FlussonicStreamsService` directly (`findAllForCustomer`/`assignToCustomer`/`findAllAcrossServers`) — the only reseller-specific logic is an ownership check (`customersService.findOneForReseller(reseller.id, customerId)`, 404s if not theirs) before delegating, so a reseller gets the exact same "can't steal a stream already assigned to a different customer" 409 behavior as the admin picker for free.
- **`src/customer-auth/` is a second, fully parallel auth stack for `Customer` (not `User`)** — mirrors `src/auth/` file-for-file (service/controller/module, `*-access`/`*-refresh` strategies, guards, cookie util, `@CurrentCustomer` decorator) but is deliberately never wired together with it: separate passport strategy names (`customer-jwt-access`/`customer-jwt-refresh` vs `jwt-access`/`jwt-refresh`), a separate refresh cookie (`customer_refresh_token`, path `/api/v1/customer-auth`, vs `refresh_token` at `/api/v1/auth`), and both access/refresh payloads carry a `type: 'customer'` marker checked in `validate()` — belt-and-suspenders against a token from one stack ever authenticating on the other, even though both currently sign with the same `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET` (safe today since `users.id` is a UUID and `customers.id` is a bigint, so `sub` values can never collide, but the `type` check doesn't depend on that fact holding). `POST /customer-auth/login` accepts `identifier` (phone number **or** username — `CustomersService.findByIdentifierWithPassword` matches either column) + `password`; only `CustomerStatus.ACTIVE` customers can log in or keep an existing session valid (checked both at login and on every access-token validation, same as `UserStatus.ACTIVE` for admin/user). There is no customer self-registration — accounts are created by an admin via the existing `customers` CRUD.
- **`GET /customer-auth/streams` is customer-scoped by token, not by request param**: `CustomerStreamsPortalController` (same module) takes the customer id from `@CurrentCustomer()`, never from the URL/query — a logged-in customer can only ever see `FlussonicStreamsService.findAllForCustomer(<their own id>)`, with no path that accepts an arbitrary customer id the way the admin-only `customers/:id/streams` does.
- **`flussonic_streams.customer_id` is a plain nullable FK (no DB constraint), enforcing 1 customer : N streams at the app layer**: a stream has at most one customer; a customer can have many streams. `FlussonicStreamsService.assignToCustomer(customerId, streamIds)` (called from `CustomerStreamsController`, `customers/:id/streams`) does a full replace — any stream currently assigned to that customer but missing from the new `streamIds` list is unassigned (`customer_id = null`), and everything in the list is assigned to it — rather than incremental add/remove calls. It first checks every requested id isn't already `customer_id`-set to a *different* customer (409 `Conflict` naming the offending stream(s) if so) — there's no "steal" or override path, unlike stream name overwrites elsewhere. `GET /flussonic-streams` (`FlussonicStreamsDirectoryController`, top-level, not nested under a server) is a separate cross-server search used only by the customer-assignment picker UI: its `availableForCustomerId` filter returns `customer_id IS NULL OR customer_id = :id`, so a stream owned by another customer is invisible to that picker entirely (not just disabled) — the frontend never has to defend against selecting an unavailable stream. Both this controller and `CustomerStreamsController` return `FlussonicStreamDirectoryEntry` (id/name/server_id/server_name/customer_id/status), a flattened shape built by `FlussonicStreamsService.toDirectoryEntries` — not the raw `FlussonicStream` entity — since callers need the owning server's name without a manual join.
- **`customers` and `flussonic_servers` never hard-delete** — `remove()` in both services sets `status = *Status.DELETED` and saves instead of calling `repository.remove()`. `findAll`/`findOne` in both services always exclude `status = DELETED` (via a `where`/`Not()` clause), so soft-deleted rows disappear from every normal read path but the row physically remains. `create`/`update` reject `status: 'deleted'` in the request body with a 400 (`assertSettableStatus`) — deletion must go through the `DELETE` endpoint, not a status edit. Note: unique constraints (`customers.phone`, `flussonic_servers.(hostname, port)`) aren't relaxed for soft-deleted rows, so a deleted customer's phone number (or a deleted server's hostname:port) stays reserved and can't be reused by a new row. `users` has no delete endpoint at all, so it wasn't touched.
